# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`genericEKS/` is one of three cloud examples (`genericEKS`, `genericAKS`, `genericGKE`) under the `k8s-helm-examples` repo. It holds reference material — **not an application** — for deploying **Neo4j Enterprise on AWS EKS via the official `neo4j/neo4j` Helm chart**. There is no build/lint/test cycle; work here means editing Helm values files, Kubernetes manifests, and shell wrappers, then applying them with `helm`, `kubectl`, and `eksctl` against a live cluster.

The headline example is a **hybrid GDS cluster**: 3 core PRIMARY members + up to 2 secondary GDS members, each fronted by its own AWS NLB that terminates TLS and passes TCP to Bolt. GDS members get individual load balancers because GDS calls run over a non-routing Bolt connection. GDS is opt-in — `startall.sh --gds-count` defaults to `0` (core-only); pass `1` or `2` to add GDS secondaries.

## Deployment lifecycle

`scripts/startall.sh` and `scripts/stopall.sh` are the canonical entry points and are idempotent end to end — everything (secret, license configmap, storage classes, EFS filesystem/mount targets/CSI driver, cluster, nodegroup, Neo4j installs, load balancers) is provisioned/torn down by the scripts themselves; there's no separate manual prerequisite step. `create_storageclass.sh` and `misc-examples/createPasswordSecret.sh`/`misc-examples/create-licenses-configmap.sh` still exist standalone (and `startall.sh` calls `create_storageclass.sh` itself, but not the two under `misc-examples/`), but running the full scripts is the normal path.

`startall.sh` takes a mode argument (defaults to the full pipeline with no arguments); `stopall.sh` takes independent, combinable options and does nothing (just shows usage) with no arguments, since it's destructive:

```bash
# Bring up just the k8s/AWS infrastructure (cluster, nodegroup, namespace,
# secret/licenses, EFS, storage classes) without installing Neo4j:
scripts/startall.sh --k8s

# Full pipeline: k8s infrastructure + Neo4j installs + load balancers.
# Also what runs with no arguments at all.
scripts/startall.sh --all

# Tear down Neo4j only (helm uninstall + wipe data/transactions PVs):
scripts/stopall.sh --uninstall-neo4j

# Also delete the 3 load balancers:
scripts/stopall.sh --uninstall-neo4j --undeploy-lb

# Full wipe: Neo4j + load balancers + nodegroup + EKS cluster + EFS.
# --all implies --uninstall-neo4j and --undeploy-lb (skipping either would
# orphan still-billing AWS resources once the cluster is gone -- see
# scripts/stopall.sh's header comment).
scripts/stopall.sh --all
```

Single-member / standalone deploys use `helm upgrade -i <release> neo4j/neo4j -f <values>.yaml` directly.

## Key conventions

- **Services disabled in chart, load balancers external.** Every values file sets `services.neo4j.enabled: false`. LBs are standalone `Service` manifests (`lb-neo4j-core.yaml`, `lb1-gds.yaml`, `lb2-gds.yaml`, `misc-examples/standalone-lb.yaml`) so their IPs/ACM certs survive `helm uninstall` — this repo has no DNS, so a recreated LB with a new IP would break the TLS certs. Do **not** re-enable chart services to "simplify"; it defeats this design.
- **LBs require AWS Load Balancer Controller.** The `service.beta.kubernetes.io/aws-load-balancer-*` annotations (nlb, TCP backend, ACM cert ARN) are only reconciled into a real NLB if the AWS Load Balancer Controller is actually running in the cluster (`helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system --set clusterName=<cluster> --set region=<region> --set vpcId=<vpc-id>`). `awsLoadBalancerController: true` in the nodegroup's `iam.withAddonPolicies` (see `eks_create_cluster*.yaml`) only grants the node role IAM permissions — it does **not** deploy the controller; without it, `LoadBalancer` Services sit at `<pending>` forever. The `service.beta.kubernetes.io/aws-load-balancer-ssl-cert` annotation is a placeholder — replace `YOUR ACM ARN GOES HERE` with a real ACM cert ARN **in the same AWS account and region as the cluster** (an ARN from another account fails `CreateListener` with a `ValidationError`); if no cert exists yet, comment out both the `ssl-cert` and `ssl-negotiation-policy` annotations and change the `http` Service port from `443` to `80` (plain TCP passthrough to 7474 — port 443 without TLS is misleading, so the LB listens on 80 in that mode) to fall back cleanly to unencrypted HTTP.
- **Images.** `neo4j-core.yaml`/`hybrid-neo4j-gds.yaml` use the official multi-arch Neo4j Enterprise image (works on the ARM64 nodegroups here — `m7g`, `r7g`, `r6g` — keep image arch and instance arch aligned if this ever changes). Both files have a commented-out `customImage` pointing at a private ECR repo (`...drose-repo:neo4j-axeb...-enterprise-arm`) in a *different* AWS account (`766746056086`) — don't uncomment it without cross-account ECR pull access, or every pod 403s on `ImagePullBackOff`. That custom image had GDS baked in (built from `docker/axb-debug`/`docker/axbg-debug`, `docker buildx build --platform linux/arm64 ... --push` — see `docker/README.md`); the official image doesn't, so `hybrid-neo4j-gds.yaml`'s `NEO4J_PLUGINS` env var includes `"graph-data-science"` to install it instead.
- **Licenses mounted, not baked.** `gds.enterprise.license_file` / `dbms.bloom.license_file` point at `/licenses/local/*.license`, fed by the `license-config` configmap via `additionalVolumes`/`additionalVolumeMounts`. Bloom is served as an unmanaged extension (`server.unmanaged_extension_classes: com.neo4j.bloom.server=/bloom`).
- **Storage.** `data` and `transactions` volumes use dynamic provisioning against the `gp3highiops` StorageClass (`WaitForFirstConsumer` so PV lands in the pod's AZ; `reclaimPolicy: Retain`). Despite `Retain`, `stopall.sh` explicitly deletes every release's `data-*`/`transactions-*` PVCs *and* their bound PVs on every run — teardown is a full wipe by design here, not an accidental one; `Retain` only prevents the PV from being silently reclaimed by some other process in between. `backup`/`import` volumes bind a shared EFS PVC (`pvc-efs-dynamic`, `sc-efs-dynamic` StorageClass) for RWX access — `stopall.sh` does not touch this one, since it's shared across releases rather than owned by any single one. `startall.sh` provisions the whole EFS stack itself and is idempotent: an EFS filesystem (found/created by a stable creation token `<cluster>-efs`), a security group allowing NFS/2049 from the VPC CIDR, mount targets in every node subnet, and the AWS EFS CSI driver via Helm — then substitutes the real filesystem ID into `storageclass/sc-efs-dynamic.yaml` (checked-in file has a `FILESYSTEM_ID_PLACEHOLDER`, since a real ID from one account/cluster won't exist in another) before applying it and `pvc/efs-pvc-dynamic.yaml`. See `efs-notes/` for the old manual process this replaced. Because the EFS filesystem/mount targets/security group are created directly via the AWS CLI, CloudFormation has no idea they exist; `stopall.sh --all` deletes them explicitly *before* attempting cluster deletion, since a leftover mount-target ENI in a node subnet makes that Subnet resource permanently fail to delete ("has dependencies and cannot be deleted"), leaving the whole cluster CloudFormation stack stuck `DELETE_FAILED`. As a backstop for any other unforeseen leftover dependency, `stopall.sh`'s stack deletions retry with `aws cloudformation delete-stack --deletion-mode FORCE_DELETE_STACK` if the normal deletion doesn't succeed.
- **Cluster topology in config, not chart flags.** PRIMARY/secondary roles come from Neo4j config keys (`initial.server.mode_constraint`, `initial.dbms.default_primaries_count: 3`, `minimumClusterSize: 3`), plus `nodeSelector`/`labels` (`eks.amazonaws.com/nodetype: primary`) to pin members to nodegroups and let LB selectors target them.

## Gotchas

- `stopall.sh` manually deletes leftover `*-cleanup` pods in the `neo4j-ns` namespace after `helm uninstall` — the chart's cleanup jobs don't always clear on their own. Most resources here assume the `neo4j-ns` namespace.
- Release names, values files, and nodegroup names in `scripts/startall.sh`/`stopall.sh` are hardcoded (`neo4j-1..3`, `neo4j-gds-1..2`, `--include=neo4j-ng`); they must stay consistent with `eks_create_cluster*.yaml` nodegroup names, and the `app` label everywhere it's used for selection: `neo4j-core.yaml`/`hybrid-neo4j-gds.yaml`'s `neo4j.name` (must match between the two, or GDS secondaries can only discover each other and never join the real cluster — they hang forever on startup with no error), and `lb-neo4j-core.yaml`'s Service `selector.app` (must equal that same `neo4j.name`, or the LB has zero endpoints and every target shows unhealthy with no traffic getting through at all). `neo4j-core.yaml`/`hybrid-neo4j-gds.yaml` hardcode `nodeSelector: eks.amazonaws.com/nodegroup: "neo4j-small"`, but `startall.sh --nodegroup NAME` (core, default `neo4j-small`) and `--gds-nodegroup NAME` (GDS, default `gdslarge`) override it per install by writing substituted temp copies (`deployed-<cluster>-<release>/core-values-N.yaml` / `gds-values-N.yaml`) rather than editing those files. The two are kept separate because GDS wants roughly 2x the CPU/memory of the core members — so each `--domain-name` deployment can pin its core members to one nodegroup (e.g. `customers` on `neo4j-small`, `claims` on `neo4j-4xlarge`) while its GDS secondaries land on the larger, shared-by-default `gdslarge`. Because `gdslarge` defaults identically across every domain, `stopall.sh --all` for one domain will delete it out from under any *other* domain's still-running GDS members unless that domain is torn down in the same invocation — see `NODEGROUPS_TO_DELETE` in `stopall.sh`.
- `startall.sh --cluster-name`/`--release-name` override the EKS cluster name and Helm release prefix (both default `jhair-cluster`/`neo4j`). Since eksctl rejects `--name` alongside `--config-file`, a custom cluster name is applied by writing a temp copy of `eks_create_cluster-jhair.yaml` (with `metadata.name` substituted) into `deployed-<cluster>-<release>/` — a gitignored, per-deployment scratch directory (see `.gitignore`'s `deployed-*/` pattern) — cleaned up via an `EXIT` trap. A custom release name also needs `lb1-gds.yaml`/`lb2-gds.yaml`'s `helm.neo4j.com/instance` selector substituted at apply time (piped through `sed` rather than `kubectl apply -f` directly), since those LBs select GDS pods by exact release name — `lb-neo4j-core.yaml` doesn't need this, its selector is release-name-independent (matches on `app`/`nodetype`, not `helm.neo4j.com/instance`).
- `startall.sh` writes `deployed-<cluster>-<release>/deployment.env` (cluster name, release prefix, GDS count, namespace, core nodegroup, GDS nodegroup) on every run — one directory per cluster+release combination, so deploying several side by side doesn't clobber each other's record. `stopall.sh` discovers these via a glob (`deployed-*`, narrowed by `--cluster-name`/`--release-name` if given) and sources whichever one it resolves to, so it tears down whatever was *actually* deployed without repeating those flags. This includes regenerating its own temp `ClusterConfig` copy for `eksctl delete nodegroup`/`eksctl delete cluster`, since those also read the cluster name from the config file's `metadata.name`, not a flag. If the glob matches more than one directory, `stopall.sh` refuses to guess and lists them, asking for `--cluster-name`/`--release-name` to disambiguate — silently picking one could tear down the wrong cluster. If nothing matches at all (e.g. `deployed-*/` was cleaned, or `startall.sh` was never run from this checkout), it falls back to `jhair-cluster`/`neo4j`/GDS count `2` — the max footprint, since over-attempting cleanup is harmless (`--ignore-not-found` throughout) but under-attempting it can orphan real resources. On a successful `--all` teardown, the matched `deployed-*/` directory is removed too, so it doesn't linger as a stale ambiguous match later.
- `startall.sh --gds-count {0,1,2}` (default `0`) controls how many GDS secondaries get deployed; `GDS_LBS` is sliced from a 2-element array (`GDS_LBS_ALL[@]:0:GDS_COUNT`) so `--gds-count 1` only creates/waits-on `lb1-gds.yaml`. When `GDS_COUNT` is `0`, the GDS helm-install loop, the GDS LB apply loop, and the final `ALTER DATABASE ... SECONDARY` instruction are all skipped (an empty `GDS_LBS` array makes the loops naturally no-op; the `ALTER DATABASE` message is explicitly gated since "0 SECONDARY" isn't a useful instruction to print). `stopall.sh` picks this up automatically too via `deployment.env` (see above).
- `misc-examples/` holds root-level files that exist for reference but aren't read by `startall.sh`/`stopall.sh` at all: `create-licenses-configmap.sh`/`createPasswordSecret.sh` (the scripts' own inline equivalents replaced these), `eks_create_cluster2.yaml` (an alternate/legacy cluster config, not `CLUSTER_CONFIG`), `standalone.yaml`/`standalone-lb.yaml` (single-member deploy example), `neo4j-lb.yaml` (an older, still-`efs`-namespaced LB example predating the `neo4j-ns` rename), `neo4j-K8s-lb-sample.txt`, and `externalDNS.zip`.
- Some Neo4j settings (the `initial.*` namespace — e.g. `initial.dbms.default_primaries_count`, `initial.dbms.automatically_enable_free_servers`) are only read once, at initial DBMS/database bootstrap. A plain `helm upgrade` won't apply a changed value to an already-bootstrapped cluster. If a config change needs a from-scratch bootstrap to take effect, a rolling restart isn't enough — uninstall and let `stopall.sh` wipe the `data`/`transactions` PVs (see Storage above), then reinstall via `startall.sh` so the database initializes fresh with the new settings.
- `stopall.sh` deletes the nodegroup with `--disable-eviction`. When it's the cluster's only nodegroup, `eksctl` cordons every node before draining any of them, so 2-replica `kube-system` deployments behind a PodDisruptionBudget (`coredns`, `ebs-csi-controller`, `metrics-server`) can never reschedule their 2nd replica and block eviction forever ("N pods are unevictable"). `--disable-eviction` bypasses the PDB, which is safe since those pods are being destroyed with the nodegroup anyway.
- `db.tx_log.rotation.retention_policy: "1 hours"` in the values files is a **testing-only** setting — production tx-log retention must match the backup/store-copy strategy.
- Reaching the GDS secondary through a composite database (`CREATE ALIAS <composite>.<alias> FOR DATABASE <db> AT 'neo4j+ssc://...'`) needs three things, and the failure modes for missing each are misleading:
  - `initial.server.tags: "gds"` is also bootstrap-only (like the `initial.*` settings above) — if the GDS server already registered before the tag was added, a redeploy won't apply it. Fix live with `ALTER SERVER '<server-id>' SET OPTIONS {tags: ['gds']}` (id from `SHOW SERVERS`), no restart needed.
  - The alias's `AT` URL must point directly at the GDS-specific LB (e.g. `lb1-gds.yaml`'s Service), not the shared core LB. `dbms.routing.default_router: "SERVER"` (see access-outside-k8s comment in `neo4j-core.yaml`/`hybrid-neo4j-gds.yaml`) makes every real client connection collapse to "whichever server I'm actually talking to," so a `dbms.routing.load_balancing.config.server_policies.gds: tags(gds); halt();` policy referenced via `?policy=gds` in the URL is inert for live queries through the shared core LB — it only affects the output of `CALL dbms.routing.getRoutingTable({policy:'gds'}, '<db>')`, not what a real session actually does.
  - The client session must request **read-only access mode** — `cypher-shell --access-mode read` (default is `write`), or Neo4j Browser's connection-level "Read Only" toggle. Under `default_router: SERVER`, a write-mode session gets steered toward a writable core member (the GDS secondary, `mode_constraint: SECONDARY`, is never eligible), so any GDS procedure call through the alias fails with a confusing `42N08: no such procedure` — indistinguishable from a real missing-plugin error — instead of an access-mode error.
  - This confines the alias to `READ`-mode GDS procedures: `SHOW PROCEDURES YIELD name, mode` shows `.stream` and, less obviously, `.mutate` (it only writes into GDS's private in-memory graph catalog, never the actual Neo4j store, so Neo4j classifies it as `READ`) both work fine. `.write` variants are `WRITE`-mode and structurally unreachable through the alias either way: read-mode rejects them outright (`42N02: writing in read access mode not allowed`) and write-mode gets redirected off the GDS server as above. `.write` also independently requires a valid GDS Enterprise license to run at all when the target is a `SECONDARY` (`IllegalStateException: Writing results to the cluster is only available with a Licensed Neo4j Graph Data Science library deployed on a Secondary instance`) — confirmed even calling it directly against the GDS pod, bypassing the alias/routing entirely.
- `clientSamples/` holds real customer-derived variants (Cilium, external-DNS, blue/green, multi-region LB) — treat as reference snapshots, not the canonical examples.
